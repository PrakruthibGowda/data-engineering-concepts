## How Does Data in the OLTP World Translate into OLAP?

This is essentially the core of data warehousing: turning OLTP operational data into OLAP analytical models (fact and dimension tables).

---

### 1. Start with OLTP (Operational Database)

OLTP databases store transactional data optimized for fast inserts/updates and are usually normalized (3NF).

**Example OLTP schema for an e-commerce system:**

**Orders table:**

| order_id | customer_id | product_id | quantity | order_date |
|----------|-------------|------------|----------|------------|

**Customers table:**

| customer_id | name | city | country |
|-------------|------|------|---------|

**Products table:**

| product_id | product_name | category | price |
|------------|--------------|----------|-------|

These tables are:

- Highly normalized
- Designed for transactions
- Not optimized for analytics queries like — *"total revenue by category by month"*

---

### 2. Extract OLTP Data

Data is extracted from operational systems using:

- ETL pipelines
- CDC (Change Data Capture)
- Batch jobs
- Streaming pipelines

#### Example Tools

| Tool | Description |
|------|-------------|
| **Airbyte** | Open-source data integration platform that enables standardized ELT pipelines by syncing data from various sources to warehouses and databases. |
| **Fivetran** | Fully managed, automated data pipeline provider that extracts, loads, and syncs data from hundreds of SaaS and database sources into cloud warehouses with minimal engineering effort. |
| **Debezium** | Open-source, distributed change data capture (CDC) platform built on Apache Kafka that streams real-time, row-level database changes into event-driven systems. |
| **Kafka** | Software interface — such as a client library, configuration module, or infrastructure plugin — that enables applications to produce, consume, and manage data streams within Apache Kafka clusters. |
| **Custom Python/Spark jobs** | Hand-rolled extraction scripts tailored to specific business logic. |
   
---

### 3. Load Raw Data into Warehouse (Staging Layer)

   PostgreSQL OLTP ──▶ Raw data copied ──▶ Data warehouse staging layer

Before modeling, raw data is loaded into a **staging** or **raw** schema. These tables often resemble the OLTP structure.

   >raw.orders, raw.customers, raw.products


---

### 4. Transform Data for Analytics

Now transformations begin to prepare data for analytics.

**Common transformations:**

- Cleaning bad records
- Type conversions
- Deduplication
- Deriving metrics
- Joining related tables
- Creating time attributes

>text revenue = quantity × price


---

## 5. Build Dimensions (Descriptive Data)

Dimension tables describe business entities.

**Examples:** Customers, Products, Locations, Time

Dimensions contain attributes used for **filtering** and **grouping**.

> [!NOTE]
> - Uses a **surrogate key** (e.g., `customer_key`)
> - Stores descriptive attributes
>
> **Surrogate Key:** A surrogate key is a unique, system-generated identifier that holds no business context, providing a stable and compact way to manage changing data and ensure consistency within a data warehouse.

### DimCustomer

| customer_key | customer_id | name | city | country |
|--------------|-------------|------|------|---------|

### DimProduct

| product_key | product_id | product_name | category |
|-------------|------------|--------------|----------|

### DimDate

| date_key | date | month | quarter | year |
|----------|------|-------|---------|------|

---

## 6. Build Fact Tables (Measurements)

Fact tables store measurable business events.

**Examples:** Sales, Orders, Revenue, Clicks, Transactions

**Fact tables contain:**

- Foreign keys to dimensions
- Numeric metrics *(rule of thumb)*

### FactSales

| date_key | product_key | customer_key | quantity | revenue |
|----------|-------------|--------------|----------|---------|

**Example row:**

| date_key | product_key | customer_key | quantity | revenue |
|----------|-------------|--------------|----------|---------|
| 20260311 | 45          | 102          | 3        | 90.00   |

**Meaning:**

- Customer **102** bought
- Product **45**
- On **March 11**
- Quantity = **3**
- Revenue = **90**

---

### 7. Resulting OLAP Star Schema

The warehouse now looks like this:
>FactSales—> DimDate, DimCustomer, DimProduct

This is called a **Star Schema**.

**Benefits:**

- ⚡ Fast aggregations
- 🔍 Simple analytical queries
- 🔗 Reduced joins

---

### 8. Example OLAP Query

**Business question:** *Revenue by category per month*

      SELECT d.year, d.month, p.category, SUM(f.revenue) AS revenue FROM fact_sales f JOIN dim_date d ON f.date_key = d.date_key JOIN dim_product       p ON f.product_key = p.product_key GROUP BY d.year, d.month, p.category;      

This query would be **slow on OLTP** but **very fast on OLAP**.
